Agent 时代，哪些架构设计方法仍然有效？

在大模型、Vibe Coding 和 Coding Agent 爆发的当下，代码生产速度远超质量保障速度。
架构方法没有过时，但价值重心发生了深刻位移。

Architecture Notes ·2026 年 6 月 ·8 分钟阅读

核心判断

大部分架构方法仍然有效，但它们的「价值重心」发生了位移——从「指导人写代码」转向「约束 Agent 不要写错代码」。

在代码写得越来越快的时代，约束比实现更重要。

· · ·

一、价值被放大的方法

价值放大 质量属性驱动的架构设计（ADD / ATAM）

以前 ATAM 的痛点是需要大量时间做效用树、识别敏感点和权衡点。但在 Agent Coding 时代，这些方法的价值反而提升了。因为 Agent 不理解你的质量属性上下文。

ATAM 中「架构驱动因素」的识别，变成了人和 Agent 之间最关键的接口。人不写代码了，但人必须写清楚这些约束。

价值放大 模块化分解与接口契约设计

Agent 能在模块内部快速生成大量代码，但如果模块边界不清、接口定义模糊，集成会变成灾难。

你不需要管 Agent 怎么命名变量，但你需要管两个模块之间的契约是什么。

价值放大 架构决策记录（ADR）

Agent 每次会话没有长期的上下文记忆。ADR 提供了人和 Agent 之间的决策上下文传递机制。

价值放大 自动化质量门禁

架构约束如果不能被自动化验证，在 Agent 高速产出代码的环境下就等于没有约束。

· · ·

二、需要调整用法的方法

需要调整 架构风格的选择

现在要多考虑一个维度：哪种风格对 Agent 更友好、更容易约束。六边形架构对 Agent 非常友好，因为端口接口是人为定义的契约。

需要调整 迭代和增量开发

迭代的重点从「产出了多少代码」转向「验证了多少架构假设」。

需要调整 代码评审

焦点从「逐行看逻辑」转向「评审架构符合性和集成风险」。

· · ·

三、价值明显下降的方法

价值下降

详细的实现级设计（类图、时序图细化）· 编码规范层面的管控 · 以人力估算为基础的项目管理

· · ·

总结

人负责：定义质量属性 → 划分模块边界 → 定义接口契约 → 记录架构决策 → 设置自动化架构约束

Agent 负责：在契约内生成实现 → 补充单元测试 → 填充适配器 → 生成样板代码

自动化负责：验证契约合规性 → 检查架构 Fitness Function → 运行质量门禁

架构方法没有过时，但价值重心从「指导实现」转移到了「定义边界和约束」。在代码写得越来越快的时代，约束比实现更重要。
