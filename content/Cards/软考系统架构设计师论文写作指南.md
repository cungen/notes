# 系统架构设计师论文写作指南

> 基于历年真题分析，选取三类代表性论文题目，拆解其写作结构、思路和套路。
> 考试要求：120 分钟内完成约 2000-2500 字的论文。

---

## 一、论文通用结构（三段式）

所有论文题目都按相同的三段式提问，对应论文的三个核心段落：

```
┌─────────────────────────────────────────────────┐
│ 摘要（200-300 字）                                │
│  项目背景 + 采用的技术方法 + 最终效果              │
├─────────────────────────────────────────────────┤
│ 正文一：项目背景（400-500 字）                     │
│  - 项目名称、时间、规模、业务领域                   │
│  - 你在项目中的角色和主要职责                      │
│  - 项目的架构概貌（简要描述）                      │
├─────────────────────────────────────────────────┤
│ 正文二：技术论述（800-1200 字）★ 核心得分区        │
│  - 题目要求的技术/方法的原理和分类                  │
│  - 在项目中如何具体应用（结合架构图/流程说明）       │
│  - 关键设计决策和理由                              │
├─────────────────────────────────────────────────┤
│ 正文三：问题与解决（400-500 字）                   │
│  - 实施中遇到的具体问题（1-2 个）                   │
│  - 采取的解决手段                                  │
│  - 解决后的效果（量化指标更佳）                     │
├─────────────────────────────────────────────────┤
│ 总结（100-200 字）                                │
│  - 项目成果回顾                                    │
│  - 个人收获与不足                                  │
└─────────────────────────────────────────────────┘
```

### 关键评分点

| 评分维度 | 占比 | 说明 |
|----------|------|------|
| 项目真实性 | ~20% | 项目描述要具体、合理，避免空洞 |
| 技术深度 | ~35% | 正文二的核心，原理 + 应用 + 决策 |
| 问题解决 | ~25% | 正文三，需要真实感的问题和解决过程 |
| 结构与表达 | ~20% | 逻辑清晰、术语准确、段落分明 |

## 二、代表性论文一：新兴技术类

### 📌 题目示例（2022 真题）

> **论湖仓一体架构及其应用**
>
> 请围绕"论湖仓一体架构及其应用"论题，依次从以下三个方面进行论述：
> 1. 概要叙述你参与设计的软件项目以及你在其中所承担的主要工作。
> 2. 详细描述湖仓一体架构的核心概念、关键技术和优势。
> 3. 具体阐述你参与的软件项目是如何应用湖仓一体架构的，过程中遇到哪些问题，是如何解决的。

### 写作思路

```
摘要：我在 XX 公司参与了"智能物流数据分析平台"项目，采用湖仓一体架构
解决了数据湖治理难 + 数仓成本高的问题，实现了 TB 级数据的实时分析能力。

正文一（项目背景）：
- 项目：智能物流数据分析平台，为全国 300+ 仓库提供数据分析
- 角色：系统架构设计师，负责整体数据架构设计
- 背景：原有系统用传统数仓（Greenplum），成本高且无法处理非结构化数据
- 架构概貌：数据源 → 数据入湖 → 湖仓一体层 → 分析服务 → BI/报表

正文二（技术论述）：
  2.1 湖仓一体概念
  - 数据湖的灵活性 + 数据仓的结构化治理
  - 核心特征：ACID 事务、Schema 演化、时间旅行、存算分离

  2.2 关键技术选型
  - 存储层：Apache Iceberg（表格式管理）
  - 计算层：Apache Spark + Flink（批流一体）
  - 元数据：Hive Metastore → 自建元数据中心
  - 架构图：[画出分层架构]

  2.3 项目中的应用
  - 统一数据入湖：Kafka + Flink CDC 实时入湖
  - 分层管理：ODS → DWD → DWS → ADS，每层用 Iceberg 表管理
  - 查询引擎：Presto 做即席查询，Spark 做批量 ETL
  - 数据治理：统一权限、血缘追踪、数据质量监控

正文三（问题与解决）：
  问题一：小文件过多导致查询性能下降
  - 原因：Flink 实时写入产生大量小文件
  - 解决：引入 Compaction 策略，定时合并小文件，查询性能提升 60%

  问题二：Schema 演化导致下游任务失败
  - 原因：业务方频繁加字段，未通知下游
  - 解决：引入 Schema Registry + 兼容性检查机制，变更前自动校验

总结：
项目上线后，数据查询时效从 T+1 提升到分钟级，存储成本降低 40%。
个人收获：深刻理解了湖仓一体在"灵活性 vs 治理性"之间的平衡设计。
```

### 此类论文的通用套路

新兴技术类题目（微服务、云原生、区块链、湖仓一体等）的写作框架一致：

1. **讲清概念**（是什么、解决什么问题、核心特征）
2. **讲清技术选型**（有哪些实现方案、你选了什么、为什么）
3. **讲清落地过程**（架构分层、数据流、关键组件）
4. **讲清踩坑**（至少 1 个具体问题 + 解决方案 + 量化效果）

## 三、代表性论文二：传统架构方法论类

### 📌 题目示例（2019 真题）

> **论软件系统架构评估及其应用**
>
> 请围绕"论软件系统架构评估及其应用"论题，依次从以下三个方面进行论述：
> 1. 概要叙述你参与评估的软件项目以及你在其中所承担的主要工作。
> 2. 详细说明软件系统架构评估中常用的评估方法（如 ATAM、SAAM），每种方法的核心步骤。
> 3. 结合项目，详细论述你采用了哪种评估方法，评估过程和结果如何，发现了哪些问题。

### 写作思路

```
摘要：我在 XX 银行参与了"信贷风控系统"的架构评估工作，
采用 ATAM 方法，识别出 3 个敏感点和 2 个权衡点，
帮助团队在性能与安全性之间做出了合理的架构决策。

正文一（项目背景）：
- 项目：银行信贷风控系统重构，日均处理 50 万笔交易
- 角色：系统架构设计师，主导架构评估
- 背景：旧系统性能瓶颈明显，重构方案有 A/B 两套，需要评估选型

正文二（技术论述）：
  2.1 架构评估方法概述
  - SAAM：关注可修改性，5 步流程
  - ATAM：关注质量属性权衡，9 步 4 阶段
  - CBAM：关注成本收益

  2.2 ATAM 核心步骤详解
  - 第1阶段（表述）：介绍方法 → 业务驱动 → 候选架构
  - 第2阶段（分析）：构建效用树 → 分析架构方法 → 记录发现
  - 第3阶段（验证）：头脑风暴 → 场景优先级投票 → 再次分析
  - 第4阶段（报告）：输出评估报告

  2.3 四个关键概念（必须写清）
  - 敏感点：某组件影响特定质量属性
  - 权衡点：某组件同时影响多个质量属性（方向冲突）
  - 风险/非风险

  2.4 项目中的实际应用
  - 构建效用树：
    - 性能：交易响应时间 < 200ms (高)
    - 安全性：数据加密传输 (高)
    - 可修改性：支持新产品类型扩展 (中)
  - 评估发现：
    - 敏感点：消息队列配置直接影响交易响应时间
    - 权衡点：加密算法选择同时影响安全性和性能

正文三（问题与解决）：
  问题一：利益相关方对质量属性优先级分歧大
  - 解决：通过效用树量化打分 + 投票机制达成共识

  问题二：方案 A 性能优但安全性弱，方案 B 相反
  - 解决：识别为权衡点，采用混合方案（关键路径加密 + 非关键路径优化）

总结：
通过 ATAM 评估，团队在方案选型上达成一致，
系统上线后交易响应时间 150ms，安全审计全部通过。
```

### 此类论文的通用套路

传统方法论类题目（架构评估、设计模式、RUP、架构风格等）：

1. **讲清方法论本身**（定义、步骤、关键概念）
2. **讲清方法之间的关系**（如有多种方法，做简要对比）
3. **讲清在项目中的具体应用**（不是复述理论，而是"我做了什么"）
4. **重点展示思维过程**（为什么选这个方法、关键发现是什么）

## 四、代表性论文三：企业集成类

### 📌 题目示例（2020 真题）

> **论企业集成架构设计及其应用**
>
> 请围绕"论企业集成架构设计及其应用"论题，依次从以下三个方面进行论述：
> 1. 概要叙述你参与设计的软件项目以及你在其中所承担的主要工作。
> 2. 详细说明三类企业集成架构设计技术（数据集成、应用集成、企业集成平台）。
> 3. 结合项目，详细论述你参与了怎样的企业集成架构设计，遇到了哪些问题，如何解决的。

### 写作思路

```
摘要：我在 XX 集团参与了"统一业务中台集成平台"项目，
设计了基于 ESB + API 网关的企业集成架构，
整合了 12 个遗留系统，实现了业务流程的自动化协同。

正文一（项目背景）：
- 项目：大型制造集团业务中台建设，整合 ERP、CRM、WMS 等系统
- 角色：系统架构设计师，负责集成架构设计
- 背景：各系统独立建设 10+ 年，数据孤岛严重

正文二（技术论述）：
  2.1 企业集成的三个层次
  - 数据集成：ETL、CDC、数据总线（共享数据库、数据仓库）
  - 应用集成：RPC、消息队列、REST API
  - 企业集成平台：ESB、API 网关、BPM 引擎

  2.2 集成架构设计
  - 核心架构：API 网关（对外）+ ESB（对内遗留系统）
  - 消息中间件：RabbitMQ 异步解耦
  - 数据同步：Canal + Kafka 做 CDC 实时同步
  - 流程编排：Camunda BPMN 引擎

  2.3 集成模式选择
  - 同步调用：REST/gRPC（实时查询场景）
  - 异步消息：MQ（订单、通知场景）
  - 事件驱动：领域事件 + 事件总线

正文三（问题与解决）：
  问题一：遗留系统接口不统一，数据格式各异
  - 解决：在 ESB 层做协议转换和消息标准化（统一为 JSON Schema）

  问题二：集成后系统间耦合导致连锁故障
  - 解决：引入熔断器（Hystrix）+ 限流 + 超时重试机制

总结：
集成平台上线后，跨系统业务流程从人工 2 天缩短到自动 30 分钟，
系统可用性从 97% 提升到 99.9%。
```

### 此类论文的通用套路

企业集成类题目（出现频率最高！）：

1. **先讲三个层次**（数据集成、应用集成、集成平台）
2. **讲清你选了哪些集成技术和为什么**
3. **重点展示集成架构图**（用文字描述各层关系）
4. **踩坑重点**：异构系统兼容性、耦合风险、性能瓶颈

## 四（续）、代表性论文四：AI/LLM 架构类（备考前瞻）

> 此类题目尚未出现在真题中，但多方预测 2026 年出现的概率极高。提前准备可以占得先机。

### 📌 预测题目

> **论 AI 模型全生命周期管理（MLOps）架构及其应用**
>
> 请围绕"论 AI 模型全生命周期管理架构及其应用"论题，依次从以下三个方面进行论述：
> 1. 概要叙述你参与设计的 AI 平台项目以及你在其中所承担的主要工作。
> 2. 详细论述 MLOps 的核心理念、关键阶段和主要技术组件。
> 3. 结合项目，说明 MLOps 架构的选型依据、落地过程中的关键挑战及应对措施。

### 写作思路

```
摘要：我在 XX 科技公司参与了"智能客服 AI 平台"项目，
设计了基于 MLOps 理念的模型全生命周期管理架构，
覆盖数据管理、模型训练、模型评估、模型部署和监控五个阶段，
将模型上线周期从 2 周缩短到 2 天，模型推理延迟降低 40%。

正文一（项目背景）：
- 项目：智能客服 AI 平台，为大中型企业提供多轮对话智能客服
- 角色：系统架构设计师，负责 MLOps 平台整体架构
- 背景：原有流程依赖手动训练和部署，模型迭代慢、质量不稳定
- 规模：日均处理 50 万通对话，模型月均迭代 3-4 次

正文二（技术论述）：
  2.1 MLOps 核心理念
  - 将 DevOps 理念延伸到 ML 领域：自动化、可复现、可监控
  - 与传统软件工程的关键区别：数据依赖 + 模型漂移 + 实验管理
  - MLOps 三个成熟度级别：Level 0（手动）→ Level 1（ML Pipeline 自动化）
    → Level 2（CI/CD + CT 持续训练）

  2.2 关键阶段与组件
  - 数据工程：数据采集 → 清洗 → 标注 → 特征工程 → 特征存储
    技术：Apache Airflow（调度）、Feast（特征存储）、Label Studio（标注）
  - 实验管理：超参搜索 → 实验追踪 → 模型评估 → 模型注册
    技术：MLflow（实验追踪）、Weights & Biases、Optuna（超参优化）
  - 模型部署：模型打包 → A/B 测试 → 灰度发布 → 推理服务
    技术：Triton Inference Server、TorchServe、KServe
  - 监控与治理：性能监控 → 数据漂移检测 → 模型重训练触发
    技术：Prometheus + Grafana、Evidently AI（漂移检测）

  2.3 项目架构设计
  - 分层架构：
    数据层：对象存储（MinIO）+ 特征存储（Feast）+ 元数据管理
    训练层：GPU 集群（Kubernetes + Volcano 调度）+ 实验追踪（MLflow）
    部署层：推理服务（Triton）+ API 网关 + 灰度发布（Istio）
    监控层：指标采集 → 漂移检测 → 自动重训练触发
  - 核心流程：数据变更 → 触发训练 Pipeline → 评估通过 → 模型注册
    → 灰度部署 → 全量上线 → 持续监控

正文三（问题与解决）：
  问题一：模型推理延迟不稳定，P99 延迟波动大
  - 原因：批量请求大小不固定，GPU 利用率忽高忽低
  - 解决：引入动态 Batching 策略 + 请求队列，设置等待窗口聚合请求
  - 效果：P99 延迟从 500ms 降到 180ms

  问题二：线上模型效果逐渐下降（数据漂移）
  - 原因：用户问法随时间变化，训练数据分布与线上分布产生偏差
  - 解决：引入 Evidently AI 做输入分布监控，设置漂移阈值自动触发重训练
  - 效果：模型准确率从月降 5% 稳定在月降 < 1%

总结：
MLOps 平台使模型迭代从"人工驱动的月度发布"升级为"数据驱动的持续交付"，
团队效率提升 3 倍，线上模型质量更稳定。
```

### 此类论文的通用套路

AI/LLM 架构类题目：

1. **讲清 MLOps 理念与传统软件工程的区别**（数据 + 模型双维度）
2. **讲清全生命周期的关键阶段**（数据 → 训练 → 评估 → 部署 → 监控）
3. **重点展示技术选型和架构分层**（为什么选这些组件、各层如何协同）
4. **踩坑重点**：推理性能优化、模型漂移、数据质量、GPU 资源调度

### 其他 LLM 方向的速记框架

| 题目方向 | 核心架构 | 关键技术点 | 踩坑方向 |
|----------|----------|-----------|---------|
| RAG 系统 | 文档解析→分块→向量化→检索→生成 | 向量库选型、混合检索、Rerank | 分块策略、幻觉控制、检索精度 |
| 多 Agent 系统 | 任务分解→Agent 编排→工具调用→记忆管理 | LangGraph/AutoGen、工具注册、上下文管理 | 任务拆分粒度、Agent 间通信、安全沙箱 |
| LLM 推理服务 | 模型加载→请求调度→推理→缓存→响应 | vLLM/Triton、KV Cache、连续批处理 | 首 Token 延迟、吞吐量、显存管理 |

## 五、备考准备清单

### 必备项目素材（至少准备 2 个项目）

每个项目需准备：

- [ ] 项目名称、时间、规模、团队人数
- [ ] 你的角色和职责（必须是"架构设计师"）
- [ ] 系统架构图（能用文字清晰描述）
- [ ] 关键技术决策和理由
- [ ] 1-2 个具体问题和解决过程
- [ ] 量化成果数据

### 推荐项目方向

| 项目类型 | 可覆盖的论文主题 |
|----------|-----------------|
| 数据分析平台 | 湖仓一体、Lambda、大数据、数据集成 |
| 微服务平台 | 微服务、云原生、分布式事务、企业集成 |
| 金融/交易系统 | 可靠性、安全性、性能、架构评估 |
| 物联网平台 | 边云协同、分布式、实时处理 |
| AI/LLM 平台 | MLOps、RAG、推理服务、Agent 架构、AI 数据治理 |

正文三（问题解决）：  25 分钟
检查 + 修改：        15 分钟
