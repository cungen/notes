## 一、为什么要做架构评估

软件架构是**最早做出的、最难修改的设计决策**。一旦代码开始编写，架构层面的缺陷修复成本呈指数级增长。因此，在编码之前对架构方案进行评估，是投入产出比最高的质量保障手段。

> 核心矛盾：**质量属性之间往往相互冲突**（如安全性与性能、可修改性与效率），架构评估的本质就是在这些冲突中找到**最优权衡点**。

## 二、三大评估方法总览

| 方法 | 关注点 | 适用场景 | 复杂度 |
|------|--------|---------|--------|
| **ATAM** | 质量属性权衡 | 需要多维度对比方案 | ★★★ |
| **SAAM** | 可修改性 | 系统演进需求明确 | ★★ |
| **CBAM** | 成本收益 | 需要做经济性决策 | ★★★★ |

> 💡 **记忆口诀**：ATAM 看权衡，SAAM 看改动，CBAM 算性价比。

## 三、ATAM — 架构权衡分析方法

> Architecture Tradeoff Analysis Method

### 3.1 核心思想

不评估"架构好不好"，而是评估"架构在**特定质量属性目标**下的表现如何"，并找出质量属性之间的**权衡点**和**敏感点**。

### 3.2 四个关键概念

```
敏感点(Sensitivity)    ── 一个组件，影响某个质量属性
权衡点(Tradeoff)       ── 一个组件，同时影响多个质量属性（且方向冲突）
风险(Risk)             ── 可能导致不良后果的架构决策
非风险(Non-risk)       ── 已验证安全的架构决策
```

### 3.3 九步流程（4 个阶段）

```
┌─────────────────────────────────────────────────┐
│ 第1阶段：表述与介绍（Step 1-3）                    │
│  ① 介绍 ATAM 方法                                │
│  ② 介绍业务驱动（目标、约束、关键质量属性）          │
│  ③ 介绍候选架构                                   │
├─────────────────────────────────────────────────┤
│ 第2阶段：调查与分析（Step 4-6）                    │
│  ④ 构建质量属性效用树(Utility Tree)               │
│     ┌─ 效用树结构：                               │
│     │  根：效用                                   │
│     │  ├─ 质量1（如：性能）                        │
│     │  │  ├─ 场景1-1 (H/M/L)                      │
│     │  │  └─ 场景1-2 (H/M/L)                      │
│     │  ├─ 质量2（如：安全性）                      │
│     │  │  └─ 场景2-1 (H/M/L)                      │
│     │  └─ ...                                    │
│     └─ 叶节点 = 具体场景 + 优先级                  │
│  ⑤ 分析架构方法（针对高优先级场景）                 │
│  ⑥ 记录：敏感点、权衡点、风险、非风险              │
├─────────────────────────────────────────────────┤
│ 第3阶段：测试与验证（Step 7-8）                    │
│  ⑦ 头脑风暴 + 场景优先级投票                      │
│  ⑧ 再次分析架构方法（针对新高优场景）              │
├─────────────────────────────────────────────────┤
│ 第4阶段：报告（Step 9）                           │
│  ⑨ 输出最终评估报告                               │
└─────────────────────────────────────────────────┘
```

### 3.4 输出物

- **效用树**（质量属性 → 场景 → 优先级）
- **敏感点清单**
- **权衡点清单**
- **风险清单**（附带风险等级）
- **架构决策记录**

## 四、SAAM — 软件架构分析方法

> Software Architecture Analysis Method

### 4.1 核心思想

以**可修改性**为主要关注点，通过"如果需求发生 X 变化，架构需要改哪里"来评估架构的**可维护性和可扩展性**。

### 4.2 五步流程

```
① 开发场景
   描述系统未来可能面临的变化需求
   例："新增支持 PostgreSQL 数据源"

② 描述架构
   用组件-连接器视图呈现候选架构

③ 场景分类
   ├─ 直接场景：现有架构无需修改即可支持
   └─ 间接场景：需要修改架构才能支持 ← 重点关注

④ 间接场景评估
   对每个间接场景：
   - 标注需要修改的组件
   - 估算修改工作量
   - 评估影响范围

   → 如果多个场景都命中同一组件 → 该组件耦合度高，需关注

⑤ 场景交互评估
   统计每个组件被多少间接场景命中
   命中越多 → 职责越不清晰 → 风险越高
```

### 4.3 输出物

- **场景列表**（直接/间接分类）
- **组件-场景映射矩阵**
- **场景交互分析**（识别高耦合组件）
- **修改工作量估算**

## 五、CBAM — 成本收益分析方法

> Cost Benefit Analysis Method

### 5.1 核心思想

在 ATAM 的基础上，不仅考虑"技术好不好"，还要考虑"**值不值得花钱做**"。给每个架构决策计算**投资回报率**。

### 5.2 流程

```
① 整理架构决策（来自 ATAM 的输出）
② 确定质量属性场景及优先级
③ 为每个方案估算：
   ├─ 收益（Benefit）：对质量属性的改善程度（1-9 分）
   ├─ 成本（Cost）：实施该方案需要的投入（人月/费用）
   └─ 计算收益率：Utility = Σ(收益 × 权重) / 成本
④ 按收益率排序，选择最优方案组合
```

### 5.3 决策矩阵示例

| 方案 | 性能收益 | 安全收益 | 总收益 | 成本 | 收益率 |
|------|---------|---------|--------|------|--------|
| A. 引入缓存 | 8 | 0 | 8 | 2人月 | 4.0 |
| B. 加密传输 | 0 | 9 | 9 | 3人月 | 3.0 |
| C. 微服务拆分 | 6 | 3 | 9 | 10人月 | 0.9 |

> 上例中，方案 A 收益率最高，优先实施；方案 C 成本过高需慎重。

## 六、对比与选择

```
你需要评估什么？
│
├─ 只关注可修改性 ──────────→ SAAM
│
├─ 多个质量属性需要权衡 ────→ ATAM
│
└─ 还要考虑成本投入 ────────→ ATAM + CBAM
```

> **实践建议**：先 SAAM 快速筛查，再 ATAM 深入分析，最后 CBAM 做经济决策。三者可以串联使用。

## 七、速记卡

```
ATAM：9步4阶段，效用树打分，找敏感点和权衡点
SAAM：5步走，场景驱动，看组件被命中次数
CBAM：收益/成本，量化排序，ROI 决策

共同点：
- 都基于「场景」驱动
- 都需要多角色参与（架构师、开发者、利益相关者）
- 都输出结构化的分析报告而非简单的好坏判断
```
