## 核心判断

大部分架构方法仍然有效，但它们的**「价值重心」发生了位移——从「指导人写代码」转向「约束 Agent 不要写错代码」**。

> 在代码写得越来越快的时代，**约束比实现更重要**。

---

## 一、价值被放大的方法

### 1. 质量属性驱动的架构设计（ADD / ATAM）

以前 ATAM 的痛点是需要大量时间做效用树（Utility Tree）、识别敏感点和权衡点，很多团队觉得「太重了」。但在 Agent Coding 时代，这些方法的价值反而提升了。

因为 **Agent 不理解你的质量属性上下文**。如果你不在架构层面把「性能要求多少 QPS」「可用性要几个 9」「可修改性要支持哪些变更场景」显式地定义出来，Agent 生成的代码会很快，但方向可能是错的。

> ATAM 中「架构驱动因素」的识别，变成了人和 Agent 之间最关键的接口。人不写代码了，但人必须写清楚这些约束。

### 2. 模块化分解与接口契约设计

这可能是当下最重要的架构活动。Agent 能在模块内部快速生成大量代码，但如果模块边界不清、接口定义模糊，Agent 生成的代码之间的集成会变成灾难。

- **DDD 的限界上下文划分**——决定哪些东西放在一起、哪些东西隔离
- **API-first / Contract-first**——先由人定义接口契约（OpenAPI spec、Protobuf、GraphQL schema），Agent 围绕契约生成实现
- **防腐层（Anti-Corruption Layer）**——隔离 Agent 在不同模块中的「风格漂移」

> 你不需要管 Agent 怎么命名变量，但你需要管两个模块之间的契约是什么。

### 3. 架构决策记录（ADR）

ADR 以前是「nice to have」的文档实践。现在变成刚需了。Agent 每次会话没有长期的上下文记忆，人也很难记住「当时为什么选了方案 A 而不是方案 B」。

ADR 本身很轻量——一个 Markdown 文件记录背景、决策、后果、备选方案——但它提供了人和 Agent 之间的**决策上下文传递机制**。

### 4. 自动化质量门禁（静态分析 + 测试金字塔）

架构约束如果不能被自动化验证，在 Agent 高速产出代码的环境下就等于没有约束。

- 测试金字塔的顶层——**契约测试（Pact）**和端到端测试——成为验证模块间交互的主要手段
- **ArchUnit / 架构 Fitness Function** 这种可以编码化的架构规则检查变得尤为重要
- CI/CD pipeline 中的质量门禁不再是锦上添花，而是防止 Agent 代码「drift」的核心机制

## 二、需要调整用法的方法

### 5. 架构风格的选择

风格本身仍然有效（分层、微服务、事件驱动、六边形架构等），但选择的侧重点变了。以前选架构风格主要考虑团队能力和运维成熟度，现在要多考虑一个维度：**哪种风格对 Agent 更友好、更容易约束**。

- **六边形架构（端口-适配器）**对 Agent 非常友好，因为端口接口是人为定义的契约，Agent 只需填充适配器实现
- 严格分层架构比「大泥球」更容易让 Agent 在受限范围内工作
- 事件驱动架构中，事件的 schema 定义本身就可以作为 Agent 的约束

### 6. 迭代和增量开发

敏捷和增量方法仍然有效，但迭代的节奏变了。以前一个 Sprint 可能产出一个功能模块；现在 Agent 可能在一天内就生成完整模块。迭代的粒度需要更细，重点从「产出了多少代码」转向**「验证了多少架构假设」**。

### 7. 代码评审（Code Review）

代码评审没有过时，但评审的焦点需要从「逐行看逻辑」转向「评审架构符合性和集成风险」。人看不了 Agent 产出的每一行代码，但可以评审：

- 是否遵守了接口契约
- 是否违反了架构约束（分层、依赖方向）
- 测试覆盖是否充分
- 是否引入了不必要的耦合

---

## 三、价值明显下降的方法

- **详细的实现级设计**（类图、时序图的细化设计）：Agent 可以直接从接口契约和需求描述生成实现，过度设计实现细节是浪费
- **编码规范层面的架构管控**：Agent 的代码风格相对统一，不需要在命名、格式上花太多架构层面的精力
- **以「人力估算」为基础的项目管理方法**：代码产出速度已经不能用人天来衡量了

---

## 四、总结：Agent 时代的架构工作框架

| 角色 | 职责 |
|------|------|
| **人** | 定义质量属性 → 划分模块边界 → 定义接口契约 → 记录架构决策 → 设置自动化架构约束 |
| **Agent** | 在契约内生成实现 → 补充单元测试 → 填充适配器 → 生成样板代码 |
| **自动化** | 验证契约合规性 → 检查架构 Fitness Function → 运行质量门禁 |

> 架构方法没有过时，但价值重心从「指导实现」转移到了「定义边界和约束」。在代码写得越来越快的时代，**约束比实现更重要**。
